# Monitor02

One-game UCLA football score-change emails are enabled for UCLA vs. Illinois on November 13, 2026 (ESPN event 401858526). The first check sets a baseline; each subsequently observed change to either team's score queues an email through the existing sender and recipient. Checks run every minute, so changes between checks can be combined. Corrections and returns to earlier scores are recorded separately. A final email is sent if the final score is unchanged. Monitoring stops after the final, with a November 15 midnight Pacific cutoff if the feed never marks the game final. Lakers and weather settings remain independent.

Temperature emails can be suspended independently with `weatherEmailsEnabled: false` in the saved monitor state. This suppresses new temperature emails and removes pending temperature emails while preserving Lakers alerts and weather readings. The background schedule must remain enabled for Lakers alerts.

Live dashboard: https://esemmelman.github.io/monitor02/

Temperature emails contain only `The current temperature is 56°`, a blank line, and today's chronological change list such as `6:33 am - 56°`. The list starts with the day's first recorded reading, omits consecutive unchanged temperatures, and uses Pacific observation times (older readings use the provider's Pacific source time). Whole numbers and degree symbols are used throughout.

Background monitoring is enabled. Supabase Cron invokes the monitor every minute, even when the page is closed or your computer is off. Weather continues daily until paused; Lakers alerts cover regulation and overtime, then automatically advance to the next unfinished game in the Lakers schedule. Sign in with your existing DayFlow account to view history, change the game date, send a test email, or pause background monitoring. Signing out does not pause it. No Gmail app password or local service is needed.

The existing DayFlow Resend sender and API credential stay server-side. No plan upgrade or new paid resource was added. Once-per-minute scheduling uses roughly 43,200 Edge Function calls in a 30-day month, plus dashboard requests. Normal Supabase, Resend and weather provider quotas apply; this is shared with other apps in the project. Provider acceptance does not guarantee inbox delivery.

Weather uses Open-Meteo current model estimates for Huntington Beach 92647, in Fahrenheit and Pacific time. Decimals are dropped with Math.trunc before comparison, recording and display: 55.2 and 55.9 both count as 55, and a change to 54.9 counts as 54 and triggers an alert. The first reading sets a whole-number baseline. Each change in that integer queues one email with all whole-number readings recorded that local day. Existing decimal history and baselines are converted on load. Larger jumps produce one email. Midnight resets the history and baseline. Short changes between samples cannot be detected.

Basketball subjects use `2nd Quarter - Lakers 94 - Milwaukee Bucks 73`, with cumulative period scores and the Lakers first. Bodies start with the Lakers' lead, deficit or tie, followed by both teams' points, rebounds and assists leaders. Score headings, timing disclaimers, retrieval timestamps and source footers are omitted. Leaders reflect the latest available statistics and may include play after the period boundary. Feed latency may delay alerts. After a final, the next scheduled game is selected using its Pacific date. Queued final alerts remain pending for delivery. If no next game is published, the schedule is checked hourly. A game still in progress stays selected across midnight. You can still select a date manually; automatic advancement resumes when that game ends.

Architecture: GitHub Pages hosts index.html, app.js, style.css and a vendored Supabase JS 2.119.0 build. The dashboard refreshes status every 15 seconds; it does not drive monitoring. cloud/index.ts is the authenticated Supabase Edge Function. cloud/core.mjs and logic.mjs contain the monitoring rules. State and queued email payloads persist in monitor02_state. An atomic database lease serializes cron requests; Resend idempotency keys help prevent duplicate retries for 24 hours. Failed sends retry at the next scheduled check. Test emails have a one-minute rate limit.

Security: browser actions require a confirmed Supabase Auth owner session and are restricted to the intended owner. The recipient is fixed server-side. Scheduler calls require a dedicated random credential stored in Supabase Vault; only its SHA-256 hash is stored in monitor02_schedule. Both monitor tables enable RLS and revoke anon/authenticated table access; server access uses the existing service role. No Resend key, service-role key, or scheduler secret is published. The function verifies authentication itself, so the gateway JWT check remains disabled. GET health exposes only service configuration status.

Deployment: apply cloud/schema.sql once, deploy cloud/index.ts with cloud/core.mjs and logic.mjs, then apply cloud/schedule.sql once. The scheduling SQL generates the secret inside Postgres and configures pg_cron plus pg_net. The named job checks the enabled flag before issuing a request. An already-running request can finish after pausing. npm test runs the monitoring tests; npm start is an optional static local preview. Legacy ignored private/ settings are unused.
